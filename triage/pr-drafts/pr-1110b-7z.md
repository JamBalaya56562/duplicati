7z was removed in 2.1.0.2 ([3f3144218](https://github.com/duplicati/duplicati/commit/3f3144218f2cdf24243fa15d78210454982c4d65), #5630), but a destination can still hold volumes from the time it was used. [Forum topic 21698](https://forum.duplicati.com/t/21698) is such a case.

Recreating the database from such a destination fails in two steps:

1. "Failed to load compression module: 7z"
2. "Detected 1 volume with missing filesets"

The database is then left in the repair state, so neither backup nor repair can go on. Nothing in the messages says that the files are 7z volumes, or how to convert them.

## The change

When the compression module of a remote volume cannot be loaded and the module is 7z, the recreate, the repair and the volume reader now say:

- that the file is compressed with 7z, which was removed in 2.1.0.2;
- that the files can be recompressed to zip with the RecoveryTool `recompress` command of 2.0.8.1, the last release with 7z.

The message is in `Strings.Common.CompressionModuleNotLoaded`. Other modules keep the old message and exception.

## Testing

- Reproduced with the official 2.4.1.0 image. I renamed a zip dlist to `.dlist.7z.aes` and recreated the database. It failed with the two messages above, as in the forum topic, and backup and repair could not continue afterwards.
  - The 2.0.6.1 and 2.0.5.1 images could not write a real 7z volume on Linux, so the test relies on the module being chosen from the file name.
