## 1. サーバの 500 — `PurgeLogData` がロックを取らずにトランザクションを開く

### 症状

Playwright の `backupRestore.spec.ts:344 › backup and restore flow` が、復元ファイル一覧の
`file.txt` をクリックできずに 30 秒でタイムアウト。その手前でサーバが 500 を返しています。

```
fail: Duplicati.WebserverCore.DuplicatiWebserver[0]
System.InvalidOperationException: The transaction object is not associated with the same
  connection object as this command.
   at Microsoft.Data.Sqlite.SqliteCommand.ExecuteReader(CommandBehavior behavior)
   at Duplicati.Server.Database.Connection.Read[T](IDbCommand cmd, Func`2 f)
   at Duplicati.Server.Database.Connection.ReadFromDb[T](Func`2 f, Action`1 prep)
   at Duplicati.Server.Database.Connection.GetBackupTargetUrls(Int64 backupId)
   at Duplicati.Server.Database.Backup.LoadChildren(Connection con)      Backup.cs:54
   at Duplicati.Server.Database.Connection.GetBackup(Int64 id)           Connection.cs:565
   at ...Endpoints.V1.Backup.BackupPost.GetBackup(...)
```

### なぜその例外になるのか

**Microsoft.Data.Sqlite は「コマンドのトランザクション」と「接続の現在のトランザクション」が
一致しないと実行を拒否します。**`cmd.Transaction` が **null** でも、接続側に開いている
トランザクションがあれば不一致です。そしてこの読み取り経路はトランザクションを付けません。

```csharp
private IEnumerable<T> ReadFromDb<T>(Func<IDataReader, T> f, Action<IDbCommand>? prep)
{
    using (var cmd = m_connection.CreateCommand())   // ← Transaction は null のまま
    ...
```

つまり**「誰かが同じ接続でトランザクションを開いている間に読むと落ちる」**という形です。

### 誰が開けたまま読ませたのか

`Connection.cs` はほぼ全てのメソッドを `lock (m_lock)` で守っています。**守っていない経路が3つ**
あります。

| 場所 | ロック | トランザクション |
|---|---|---|
| [`PurgeLogData`](Duplicati/Library/RestAPI/Database/Connection.cs:1307) | **無し** | `m_connection.BeginTransaction()` |
| [`FixInvalidBackupId`](Duplicati/Library/RestAPI/Database/Connection.cs:1181) | **無し** | 同上 |
| [`DeleteFromDb`](Duplicati/Library/RestAPI/Database/Connection.cs:1386)（`transaction == null` の枝） | **無し** | 同上 |

そして `PurgeLogData` は**タイマーのコールバックから呼ばれます** —
[`Duplicati/Server/Program.cs:536`](Duplicati/Server/Program.cs:536)、`PurgeTempFilesTimer`
（同 :544）。**別スレッドで、REST の読み取りと何の同期もなく走ります。**

**これで全部説明が付きます**: タイマーが `BeginTransaction()` してから `Commit()` するまでの
ごく短い窓に REST の読み取りが重なると、その読み取りが 500 になる。窓が短いから滅多に当たらず、
当たると差分と無関係な PR が赤くなる。**UI テストは1回の実行で何十回も REST を叩く**ので、
当たる確率がそれなりにあります。

### 直し方（#7295 でマージ済み）

`PurgeLogData` / `RegisterTempFile` / `FixInvalidBackupId` / `DeleteFromDb` の4箇所に `lock (m_lock)` を足すのが
最小です。**このクラスの既存の作法そのもの**で、判定は何も変わりません。

**測ったこと**: `m_lock` が public なので、テスト側がロックを保持したまま `PurgeLogData` を
別スレッドで呼ぶ**決定論的な**テストが書けました（`ServerDatabaseLockingTests`）。読み取りと
`PurgeLogData` を並行で回すテストは、修正前に **CI と同じ例外文言を 1 秒で再現**しています。
4箇所に `lock (m_lock)` を足して緑。Playwright のあの実行そのものは再現していません — 同じ機構で
あることは示せても、あの回がこれだったとは証明できない、と PR に書いています。

## 2. `FilesetFilesAsync` — repair が付け直す dlist の時刻

### 症状

`Unit tests (ubuntu-latest)` のみ。macOS / Windows は同じ実行で緑。

```
Failed FilesetFilesAsync [4 s]
  Assert.That(actual, Is.EqualTo(expected))
  Expected: 1
  But was:  0
  at Duplicati.UnitTest.DisruptionTests.FilesetFilesAsync() DisruptionTests.cs:line 195
```

**195行目は repair の後**の主張です。

```csharp
195: Assert.AreEqual(BackupType.FULL_BACKUP, backupTypes[1]);   // 1 = FULL, 0 = PARTIAL
```

`backupTypes` は**リモートの dlist ファイル**を**ファイル名の時刻**で並べ、中身の
`IsFullBackup` を並べたものです。直前の 186-188 行（**データベース側**の版一覧）は通っている
ので、**DB は正しく、ファイル側だけが食い違っています**。

### 怪しいのは「付け直す時刻」

repair は消えた dlist を作り直すとき、**新しいファイル名（＝新しい時刻）**を付けます。

```csharp
// RepairHandler.cs:533
var timestamp = VolumeBase.ParseFilename(n.Name).Time;             // 元の時刻
var fileTime = await FilesetVolumeWriter.ProbeUnusedFilenameNameAsync(db, m_options, timestamp, ...);
var volumeWriter = new FilesetVolumeWriter(m_options, fileTime);   // ← 名前は新しい時刻
await RunRepairDlistAsync(..., volumeWriter, n, timestamp, ...);   // 中身は元の時刻
```

`ProbeUnusedFilenameNameAsync` は**元の時刻から1秒ずつ進めて空いている名前を探します**
（`FilesetVolumeWriter.cs:287-301`、最大60回）。

テストが作る2つの版の間隔は `Thread.Sleep(2000)` の**2秒**だけで、その間に purge も
名前を1つ消費します。**古い方の版の探索が数秒進むと、新しい方の版の名前に追いつきます。**
追いつけば並び順が入れ替わり、195行目が「index 1 は FULL のはず」で PARTIAL を掴む —
観測された `Expected: 1 But was: 0` はその形です。**速いマシンほど1秒の枠に多くの操作が入り、
枠の取り合いが起きやすい**ので、Linux だけで出ることとも整合します。

### 2026-09-10 の追試 — 仮説は否定

直す前に測りました。ワークフローを `probe/**` への push で起動する形にして、**ubuntu で 105 回**
（単体 48 ＋ カテゴリ 20 ＋ coverage 付き 8 ＋ 20、`tests.yml` と同じ `--collect:"XPlat Code Coverage"`
の全スイート 2 回、ローカル 7 回）走らせて、**再現 0 回**。さらにテストを計装して測ると、2つの版の
間隔は **18 秒 / 5 秒 / 4 秒**あり、repair が動かすのは常に **+1 秒**でした。**この仮説では並びを
追い越せません。**上の「怪しいのは付け直す時刻」は、そのまま残しますが**否定済み**です。

残ったのは「落ちたときに名前が残らない」ことだけなので、[#7297](https://github.com/duplicati/duplicati/pull/7297)
で 6 つの主張すべてに dlist 名と DB の版一覧を出す診断を入れました（主張を 1 つ故意に反転させて、
文言が実際に出ることを確認）。次に落ちた 1 回で答えが出ます。

### 確かめていないこと（09-09 時点の記述）

- **ローカルで再現していません**（Windows、1回、緑）。この環境では1回 4分46秒かかるので、
  回数で殴るのは割に合いません
- 失敗時の**実際の dlist 名**が CI ログに残っていないため、上の説明は**まだ仮説**です
- 次の一手は、**失敗したときに2つの dlist 名を出す**ようにテスト側を直すこと。
  [DLIST-FLAKE-INVESTIGATION.md](DLIST-FLAKE-INVESTIGATION.md) の
  [#7177](https://github.com/duplicati/duplicati/pull/7177) と同じ手で、
  「直らないが、次の1回で答えが出る」種類の変更です

### 既知の別のフレークとは別物

[DLIST-FLAKE-INVESTIGATION.md](DLIST-FLAKE-INVESTIGATION.md) が追っているのは
