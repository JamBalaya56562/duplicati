## 原因

`sqlite_stat1` が「どのテーブルも数行」と言っているまま、テーブルが数万行に育つ。
プランナはその数字を信じて結合順を決めるので、6テーブル結合が終わらなくなる。

1. **初回バックアップで数個のファイルを「ファイルパス」として指定する。** フォルダを指定すると
   親フォルダの行が入るので、この状態にならない。ここを外していたために再現できなかった
2. 接続クローズ時の `PRAGMA optimize`（`LocalDatabase.cs:3362`）が、その小さい数字を `sqlite_stat1` に書く
3. 2回目の大きなバックアップでテーブルが膨張するが、**統計を更新する機会がない**。
   `PRAGMA optimize` はクローズ時にしか走らず、固まったバックアップはそこに到達しない
4. `LIST_FOLDERS_AND_SYMLINKS`（`LocalDatabase.cs:2427`）などが破綻する

### 再現手順

```
backup <dst> <path>\empty.txt --dbpath=<db> --no-encryption=true   # 空ファイル1つをパス指定
sqlite3 <db> "SELECT * FROM sqlite_stat1;"                         # 全て 1 になる
backup <dst> <大きなソース> --dbpath=<db> --no-encryption=true      # 固まる
```

### どのくらい小さいと壊れるか

記録された行数を強制的に変えて `LIST_FOLDERS_AND_SYMLINKS` を実測した。

| 記録された行数 | 12,103ファイル | 52,069ファイル |
|---|---|---|
| 1 | 45秒で終わらず | 45秒で終わらず |
| 2 | 45秒で終わらず | 45秒で終わらず |
| 3 | 45秒で終わらず | 0.3244秒 |
| 10 | 0.0950秒 | 0.1933秒 |
| 正確な値 | 0.0434秒 | 0.2181秒 |

**1ファイルだけの話ではない。2〜3個でも起きる。** どこで止まるかはDB次第。

**`SCAN` の数を指標にしてはいけない。** 52,069ファイルで記録値2のとき `SCAN` は0個なのに終わらない。
壊れているのは結合の順序であって走査の有無ではない。調査中この指標で一度誤った結論を出した。

### 被害は1つのクエリに限らない

`LIST_FOLDERS_AND_SYMLINKS` は `WriteFilesetAsync`（`:2484`）と `VerifyConsistency`（`:2096`、`COUNT(*)` で包む）
の両方から呼ばれる。さらに実測では **`VerifyConsistency` の長さ検査クエリ**や、
`PreBackupVerify` の**最長パス取得**（`File` ビューを読む）も同じ統計で潰れた。後者は単独で7分以上走った。

## 修正（#7181）

```
PRAGMA analysis_limit=400;
PRAGMA optimize=0x10002;
```

を `LocalDatabase.RefreshQueryStatisticsAsync` として追加し、**2箇所**から呼ぶ。

| 位置 | 守る対象 |
|---|---|
| DBを開いた直後（`PreBackupVerify`） | 前回が kill された場合。最長パス取得より前でなければ間に合わない |
| メイン処理の後 | 本命。ここまでにテーブルが膨張している |

### マスクが要る理由

`0x10000` が「接続が触っていないテーブルも見る」ビット。**これが無いと、トランザクション内では
何もしない。** `ReusableTransaction` はコミット直後に次を開くので、バックアップ中は常にトランザクション内。

```
トランザクション内:  PRAGMA optimize          0.0003秒  統計は変わらない
                     PRAGMA optimize=0x10002  0.3655秒  更新される
```

マスクを落とす変更は diff 上ほぼ無害に見えるので、`QueryStatisticsTests` で縛っている。

### 接続時の設定だけでは足りない

ts678 が `CUSTOMSQLITEOPTIONS_DUPLICATI=optimize=0x10002` を提案した。コード変更が不要で、
**kill後の実行には効く**。しかし報告されたケースには効かない — 接続を開いた時点ではテーブルが
まだ小さく、統計は正しいので、正しく何もしない。膨張はその後に起きる。

master に設定して実測（空ファイル1つ → 20,000ファイル）:

| | |
|---|---|
| 完走 | **25分でせず** |
| 低速クエリ警告 | 16件 |
| 最長のクエリ | **975.9秒 継続中** |

### 効果

| | 低速クエリ警告 | 所要 |
|---|---|---|
| master + 上記の環境変数 | 16件 | 25分で完走せず |
| #7181 | **0件** | **5分52秒** |

健全なDBでのコストは **0.0040秒**。SQLite 自身が必要性を判断するので判定は書いていない
（自作の `MAX(ID)` 判定を書いていたが、健全なDBで 0.0523秒払う劣化版だったので削除した）。

## ts678 の疑問への回答（実測済み）

- **「途中で取った統計は未コミット分を見ないのでは」** → **見る。** トランザクション内で52,069行
  追加した直後の `ANALYZE` は `104138` を記録した。だから「メイン処理の後」の呼び出しは有効
- **「`ANALYZE` を打っても直らない」** → `PRAGMA analyze` は存在しないプラグマで黙って無視される。
  また `PRAGMA optimize` は「その接続で変更したテーブル」しか見ないので、ツールで開いただけでは何もしない

## 測定に使うもの

`apsw==3.53.4.0` を使う。製品が同梱する SQLite と**同一の版**。Python 標準の sqlite3 は版が違い、
プランの測定が無意味になる。

計測スクリプトはこのディレクトリに置いていない（使い捨てのため）。
必要なら `planver.py` 相当を書き直すこと — クエリ本体は `LocalDatabase.cs:2427` にある。
