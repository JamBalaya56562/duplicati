I looked at how the release builder makes the signatures (`ReleaseBuilder/Build/Command.GpgSign.cs`, the same at the `v2.4.1.0_stable_2026-10-29` tag and on master).

- **Pairing**: yes. For each package file of the release, it runs `gpg --detach-sign` twice and puts both results in the zip: `<file>.sig` (binary) and `<file>.sig.asc` (ASCII armored). Removing `.sig` or `.sig.asc` gives the name of the release asset it signs. Both are signatures of the same file, so either one is enough.
- **Exceptions**: none in the code. Every package that the release builds is signed, so for 2.4.1.0 that should be all 49 installers and zip files on the release page. The `signatures.zip` itself is not signed. (I read this from the code; I did not download the release files.)
- **Verifying**, for example:

  ```
  gpg --verify duplicati-2.4.1.0_stable_2026-10-29-win-x64-gui.msi.sig duplicati-2.4.1.0_stable_2026-10-29-win-x64-gui.msi
  ```

  It should report the key `CBD0A83118CAFD23DF82F99CC20E90473DAC703D`.
- **The key**: the zip also has a `sign-key.txt` with the key id and two lookup URLs, `https://keys.openpgp.org/search?q=<id>` and `https://pgp.mit.edu/pks/lookup?op=get&search=<id>`. The README and `SECURITY.md` link the same key on keys.openpgp.org.

The update manifest that Duplicati downloads to check for updates is signed with its own keys, not with this GPG key.

I did not find a page that announces key rotations; that is a question for the maintainers.
