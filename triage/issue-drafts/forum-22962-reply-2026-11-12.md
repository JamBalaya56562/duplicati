The warning compares the file on the destination with what Duplicati recorded when it uploaded the file.

- **The hash**: Duplicati writes the SHA-256 hash in Base64, not in hex. That is why it has upper and lower case letters, `+`, `/` and `=`. To get the same form in PowerShell 7:

  ```
  [Convert]::ToBase64String([Convert]::FromHexString((Get-FileHash .\xxx.dblock.zip.aes -Algorithm SHA256).Hash))
  ```

  But the size is already different, so the file on the destination is not the one that was uploaded, and the hash will not match either. 1310720 bytes is exactly 1.25 MiB, which looks like a file that was cut off while it was written. That is a guess; what kind of destination is this?
- **list-broken-files**: it still exists, but it only finds volumes that are missing from the destination. A volume that is there with the wrong size is not counted.

If the files in those volumes still exist on the source, this should clean it up:

1. Move the four dblock files out of the destination folder. Keep them somewhere until the backup is fixed.
2. In the backup's menu on the home page, under "Cleanup", choose "Purge broken files". It lists the files that had data in the missing volumes and removes them from the backup versions. (On the command line, this is `list-broken-files` and then `purge-broken-files`.)
3. Run the backup. The files that still exist on the source are backed up again.

The versions of those files that only exist in older backups are lost.

It is also worth finding out why the files were cut off, so I would check the destination disk or share.
