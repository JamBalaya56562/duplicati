# `secrets.DBus.cs` の再生成に関する調査

- **調査日**: 2026-08-15
- **対象**: [`Duplicati/Library/SecretProvider/LibSecret/secrets.DBus.cs`](../Duplicati/Library/SecretProvider/LibSecret/secrets.DBus.cs)
- **きっかけ**: master のビルドに残る `CS0618`（非推奨 API）警告 10 件のうち 3 件がこのファイルから出ている
- **結論**: **再生成は可能で、非推奨 API は 0 件になる。ただし条件を完全に揃えて実行しても 1696 行が変わり、利用側の移行を伴う**
- **推奨**: **現状維持（§6 の A）。** 採取手順もソースツリーには追加しない — 理由は §6「B を見送る理由」に記した
- **訂正あり**: 初版は差分の原因を「ジェネレータの世代差」と説明していたが誤り。ツールのバージョンは無関係だった。比較は 2 度やり直しており、経緯は §5「測り直しの経緯」に残した

---

## 1. 何が起きているか

ソリューション全体を非増分でビルドすると警告 10 件・エラー 0 件。全て `CS0618` で、内訳は次のとおり。

| ファイル | 件数 | 種別 |
|---|---:|---|
| `Duplicati/Library/Backend/GoogleServices/GoogleCloudStorage.cs` | 4 | Google 認証 |
| `Duplicati/UnitTest/SecretProviderSetSecretTests.cs` | 1 | Google 認証 |
| `proprietary/GoogleWorkspace/APIHelper.cs` | 1 | Google 認証 |
| **`Duplicati/Library/SecretProvider/LibSecret/secrets.DBus.cs`** | **3** | **本レポートの対象** |
| `Duplicati/GUI/Duplicati.GUI.TrayIcon/LinuxDBusNotifier.cs` | 1 | 対応済み（[#7170](https://github.com/duplicati/duplicati/pull/7170)） |

対象 3 件の内容:

```
warning CS0618: 'DBusConnection.AddMatchAsync<T>(MatchRule, MessageValueReader<T>,
  Action<Exception?, T, object?, object?>, object?, object?, bool, ObserverFlags)' is obsolete
  ('Use the overload that accepts Action<Notification<T>> instead.')
```

該当は `secrets.DBus.cs` の 1122 / 1136 / 1150 行目。

## 2. 原因の切り分け

**ジェネレータが古いコードを出し続けているわけではない。**

`Tmds.DBus.Tool` の最新版 **0.94.2** をローカルに導入し、シグナルを 1 つ持つ最小の introspection XML から生成して確認した。出力は新しい API のみで、非推奨形は現れない。

```
WatchPingedAsync(Action<Notification<string>> handler, ObserverFlags flags, ...)
```

つまり **コミットされている生成物が、それが参照するパッケージより古いだけ**である。参照は `Tmds.DBus.Protocol` 0.94.1（`Duplicati.Library.SecretProvider` と `Duplicati.GUI.TrayIcon` の両方）。

どこまで遡っても同じである点も確かめた。`Tmds.DBus.Tool` の 0.90.0 / 0.91.0 / 0.92.0 / 0.94.2 を個別に導入し、同じ入力から生成して比較したところ、**4 つとも互いに同じ形**を出し、いずれも非推奨 API を含まない。したがって「ある時期のツールが非推奨形を出していた」という説明も成り立たない。既存の生成物は、**現行で入手できるどのバージョンでも再現できない古い形式**である（詳細は §5）。

## 3. リポジトリに欠けているもの

生成手順の記録は、生成物の冒頭 2 行しかない。

```csharp
// Autogenerated with command:
//  dotnet dbus codegen --protocol-api --service org.freedesktop.secrets
```

確認した範囲で、以下はいずれも**存在しない**。

- `dotnet-tools.json`（ジェネレータのバージョン固定）
- 再生成用のスクリプト、`.csproj` ターゲット、CI ステップ
- 生成の**入力**（introspection XML）

記録されたコマンドは `--service` 指定、すなわち**稼働中のサービスに接続して introspect する形**なので、Linux のセッションバスと `org.freedesktop.secrets` を名乗る実装が要る。Windows では再現できない。

ただし `codegen` は **XML ファイルからも生成できる**（`<files>` 引数）。入力さえ版管理下にあれば、どの環境でも再生成できる。

## 4. 採取手順（確立済み）

Docker で gnome-keyring を動かし、**7 インタフェース全部を 1 回の実行で採取できる**ところまで確認した。素朴にやると 2 つ取りこぼすので、その理由と回避策を含めて記す。

### 4.1 つまずいた点

| 問題 | 原因 | 回避策 |
|---|---|---|
| `--recurse` で `Collection` / `Item` が出ない | オブジェクトが存在しないと introspect に現れない | コレクションとアイテムを実際に作ってから、**個別のパス**を introspect する |
| `Session` / `Prompt` が出ない | **作成元の接続が切れると破棄される**。`gdbus` は呼び出しごとに別接続を張るので、次のコマンドが走る頃には消えている | **同一接続の中**で作成と introspect を行う（下記スクリプトは Python から実施） |
| `impl.portal.Secret` が出ない | 別サービスだと思われがちだが、実際は gnome-keyring 自身が**別パス**で公開している | `/org/freedesktop/portal/desktop` を introspect する |

### 4.2 採取スクリプト

[`capture-secrets-introspection.sh`](capture-secrets-introspection.sh) を参照。実行方法:

```bash
docker run --rm -i ubuntu:22.04 bash -s < triage/capture-secrets-introspection.sh > raw.txt
```

取得できるパスとインタフェースの対応:

| インタフェース | オブジェクトパス |
|---|---|
| `org.freedesktop.Secret.Service` | `/org/freedesktop/secrets` |
| `org.gnome.keyring.InternalUnsupportedGuiltRiddenInterface` | `/org/freedesktop/secrets` |
| `org.freedesktop.Secret.Collection` | `/org/freedesktop/secrets/collection/login` |
| `org.freedesktop.Secret.Item` | `/org/freedesktop/secrets/collection/login/1` |
| `org.freedesktop.Secret.Session` | `OpenSession` の戻り値（同一接続） |
| `org.freedesktop.Secret.Prompt` | `Lock` → `Unlock` の戻り値（同一接続） |
| `org.freedesktop.impl.portal.Secret` | `/org/freedesktop/portal/desktop` |

### 4.3 記録されたコマンドをそのまま再現する（推奨）

**§5 の比較に使うべきはこちらである。** 同じコンテナに .NET SDK を入れ、ライブのサービスに対して記録されたコマンドをそのまま実行する。

```bash
docker run --rm -i mcr.microsoft.com/dotnet/sdk:10.0 bash -s < reproduce.sh
```

`reproduce.sh` の中身は §4.2 のスクリプトとほぼ同じで、末尾を次に差し替えたもの。

```bash
dotnet tool install --global Tmds.DBus.Tool
dotnet dbus codegen --protocol-api --service org.freedesktop.secrets --cat
```

**セッションとプロンプトを開いたまま保持するプロセスを、codegen と並走させること。** これらは作成元の接続と共に消えるため、単に作ってから codegen を呼んでも間に合わず、生成物から `Prompt` と `Session` が黙って落ちる（§5 の測り直し 2 回目がこれ）。補助プロセスに `READY` を出力させ、それを待ってから codegen を起動する形にする。

apt の導入と NuGet の復元があるので、**上限は 45 分程度みておく**（25 分では足りず打ち切られた）。イメージ取得済みなら 2 回目以降は速い。

### 4.4 XML から生成する場合の注意

§4.2 で採取した各パスの出力から `<interface>` 要素だけを抜き出し、1 つの `<node>` にまとめて食わせることもできる。ただし**その出力を既存の生成物と比較してはいけない**。

記録されたコマンドは `--path` を指定していないため**ルートから再帰的にオブジェクトツリーを走査**する。インタフェースを平坦に並べた XML は入力の形が異なるので、出力の形も変わる。実際、この方法で得た 1631 行を既存と比べたことが、本レポート初版で「世代で形が変わった」と誤って結論づけた原因である。**比較には §4.3 を使うこと。**

## 5. なぜ差し替えで終わらないか

再生成物は既存の生成物と**構造が別物**になる。以下は §4.3 の手順、すなわち**セッションとプロンプトを開いたまま保持した状態のライブサービス**に対し、記録されたコマンドをそのまま実行して得た結果である。

```
dotnet dbus codegen --protocol-api --service org.freedesktop.secrets
```

| | 既存 | 再生成 |
|---|---:|---:|
| 行数 | 1319 | 1677 |
| 非推奨 API の出現箇所 | 17 | **0** |
| **変更行数（空白無視）** | — | **1696 行（+1025 / −666）** |

型構成も入れ替わる。

- **既存にしかない**: `PropertyChanges`, `secretsObject`, `secretsService`
- **再生成にしかない**: `ObjectFactory`, `MessageReader`, `MessageWriterExtensions`, および `ICollectionProperties` / `IChangedItemProperties` / `INullableServiceProperties` など **`I*Properties` 系インタフェース 12 個**

`Collection` / `Item` / `Service` / `Session` / `Prompt` / `Daemon` / `InternalUnsupportedGuiltRiddenInterface` と 4 つの `*Properties` は**両方に存在する**（既存は `record`、再生成は `class`）。

ヘッダの書式も変わる。既存は `// Autogenerated with command:` だが、現行ツールは `// Generated by Tmds.DBus.Tool v0.94.2 with arguments: ...` と `<auto-generated/>` を出す。

### 利用側への影響は 6 つの型に集約される

生成物の行数より、こちらのほうが移行規模の実態に近い。[`LibSecret/SecretCollection.cs`](../Duplicati/Library/SecretProvider/LibSecret/SecretCollection.cs)（481 行）が生成物から使っているのは次の 6 型だけである。

| 型 | 使用回数 | 再生成後 |
|---|---:|---|
| `secretsService` | 18 | **消える**（`ObjectFactory` へ） |
| `Service` | 7 | 残る |
| `Session` | 5 | 残る |
| `Collection` | 5 | 残る |
| `Item` | 4 | 残る |
| `Prompt` | 1 | 残る |

最も使用回数の多い `secretsService` が無くなるので、書き換えは避けられない。

### 原因はツールのバージョンではない

当初このレポートは「ジェネレータの出力形式が世代で変わったため」と説明していたが、**それは誤りだった**。0.90.0 / 0.91.0 / 0.92.0 / 0.94.2 のそれぞれで同じ入力から生成して比べたところ、**どの版も互いに同じ形**（`ObjectFactory` と `*Properties` を持つ形）を出し、**既存の形（`secretsObject` / `secretsService` / `Daemon` / `PropertyChanges`）はどの版でも再現しなかった**。

つまり既存の生成物は、**現行のどのバージョンでも再現しない、かなり以前の形式**で作られたまま据え置かれている。ヘッダ書式が違うのもその裏付けになる。

### 測り直しの経緯（同じ誤りを二度している）

上表に至るまでに、比較を **2 度やり直している**。どちらも「条件を揃えないまま数字を出した」という同じ誤りである。

| 回 | やったこと | 出た数字 | 何が間違っていたか |
|---|---|---:|---|
| 1 | 採取した 7 インタフェースを手で 1 つの `<node>` にまとめた**平坦な XML** から生成 | 1631 行 / 差分 1649 行 | 記録されたコマンドは `--path` 未指定で**ルートから再帰的に走査**する。入力の形が違えば出力の形も違う。この結果から「世代で形が変わった」と誤結論した |
| 2 | ライブサービスに対し記録されたコマンドを実行 | 1602 行 / 差分 1649 行 | codegen 実行時に**セッションとプロンプトが存在しなかった**ため、生成物から `Prompt` と `Session` が欠落していた |
| 3 | 補助プロセスが**両オブジェクトを開いたまま保持**した状態で実行（§4.3） | **1677 行 / 差分 1696 行** | — |

教訓は 2 つある。**introspection は「その瞬間に存在するオブジェクト」しか見えない**こと、そして**生成物どうしを比べる前に、入力条件が揃っているかを先に確かめる**こと。差分の大きさだけを見て原因を推測してはいけない。

いずれにせよ `Duplicati.Library.SecretProvider` の利用側コードはそのままでは通らないので、**警告 3 件を消すには LibSecret プロバイダの利用側移行が必要**という結論は変わらない。

移行後の動作確認には Linux 実機のキーリングが要る点も、規模を見積もるうえで考慮が要る。

## 6. 選択肢

| 案 | 内容 | 警告 | 規模 | 評価 |
|---|---|---|---|---|
| A | 現状維持。生成物であることを認識したうえで放置 | 3 件残る | なし | **現時点の推奨** |
| B | XML と採取スクリプトを版管理下に置き、`dotnet-tools.json` でツールを固定する | 3 件残る | 小 | **見送り**（下記） |
| C | 再生成して利用側も移行する | **0 件** | 大。Linux 実機での確認が要る | メンテナの判断待ち |

### B を見送る理由

当初は「将来の再生成の土台になる」として B を挙げたが、調査を終えたうえで**採らないほうがよい**と判断した。

**生成方法は既に記録されている。** 生成物の 1 行目にコマンドが書かれており、`Tmds.DBus.Tool` を入れれば C# に慣れた開発者はそれで足りる。ドキュメントが無いと分からない状態ではない。

**§4.1 の落とし穴を踏む機会がない。** あれらが効くのは「ライブのサービスから introspect して再生成する」場合だけである。ところが §5 のとおり再生成すると生成物の形が変わり利用側の移行を伴うので、日常的に行う作業ではない。単独では判断できない、年に一度あるかどうかの作業のために、手順書をソースツリーへ置くのは釣り合わない。

**性質が違う。** 本レポートが答えているのは「どう生成するか」ではなく「**再生成すると何が起きて、いくらかかるか**」であり、これは方針を決めるための判断材料である。リポジトリの開発者向け解説（下記の慣習）とは別物なので、triage 側に置くのが妥当と考える。

なお置き場所自体は存在する。このリポジトリには `docs/` や `CONTRIBUTING.md` は無いが、**コンポーネントの隣に `README.md` を置く慣習**があり（`Duplicati/Library/Certificates/README.md` 150 行、`Duplicati/Library/Compression/TarZstdCompression/README.md` 322 行、`LiveTests/Duplicati.Backend.Tests/README.md` ほか）、内容も実質的な開発者向け解説である。したがって仮に置くなら `Duplicati/Library/SecretProvider/LibSecret/README.md` が慣習どおりで、新しい場所を作る話にはならない。

**C に進むと決まった場合は、その移行 PR の一部として上記 README を追加するのが筋**である。手順が実際に使われる文脈ができてから置く、という順序になる。

## 7. 併記: 残る Google 認証の 6 件

同じ `CS0618` だが性質が異なるため、別扱いが妥当と考える。

```
'This method is being deprecated because of a potential security risk.
 Use the methods in the CredentialFactory class instead.
 A GoogleCredential object can then be created by calling .ToGoogleCredential()'
```

代替 API（`CredentialFactory.FromJson` / `FromFile` / `FromStream` と `.ToGoogleCredential()`）は参照中の `Google.Apis.Auth` 1.75.0 に実在することを確認済み。ただし非推奨の理由が**外部由来の認証設定の検証強化**であるため、移行すると**これまで通っていた設定が弾かれ得る**。GCS バックアップの認証経路に直結するので、警告消しとして機械的に置き換えるのは避けたほうがよい。
